# Worktree fallback

On Windows, Claude Code compares the session's folder with git's case-sensitively (a known Claude Code bug, anthropics/claude-code#91618): when the session's folder starts with a lowercase drive letter (as VS Code opens it) and git reports it uppercase, `isolation: "worktree"` is refused with "git resolves its working tree to ... (a core.worktree redirect ...)" and leaves a locked worktree behind; no `cd` outlives its call, so the session cannot fix it. Such a session makes the worktree itself: `git worktree add .tmp/wt/<name> -b wt-<name>` (under `.tmp/`, which the project's test runner excludes, like its linter). Its subagent runs every command through `node .tmp/in.js <name> <program> [args...]`, a script running it with cwd `.tmp/wt/<name>` (`spawnSync` with `cwd`, `shell: true` on Windows and `windowsHide`; a `.ps1` runs through `powershell -NoProfile -ExecutionPolicy Bypass -File` and a `.js` through `node`, never handed to the shell, which opens a script in its associated app (Notepad) instead of running it; written with `import`, never `require`, which fails in a `"type": "module"` package; a session missing it writes it again; a failed call prints no error text, so the program's own output file is read before any variant of the command is tried), uses absolute paths under `.tmp/wt/<name>/` for Edit and Write and for reading a file its branch changed (any touch of a path there injects that worktree's own `CLAUDE.md` and path rules again, so an unchanged file is read through the main tree's path, and a hunt's temporary counters go in by one `.tmp/` script patching the worktree's files and out by a patch script removing its marked lines (`git checkout` of a file drops every uncommitted edit of it, so only after committing the working state), never by Edit calls; a hunt keeps its own scripts, outputs and message files in the main tree's `.tmp/<name>/`, running them as `node .tmp/in.js <name> node ../../<name>/<script>.js`, and touches `.tmp/wt/<name>/` only for the files its branch commits; touches of worktree files are batched, since each re-injects every rule; a file changed only by uncommitted work, a resumed hunt's leftover, and a merge-in's conflict are read by `node .tmp/in.js <name> git diff -- <file>`, never by Read or Grep of the worktree path), and commits through the runner with `git commit -F ../../<name>/msg.txt` (the message written in the main tree's `.tmp/<name>/`, since any Write under `.tmp/wt/<name>/` injects that worktree's `CLAUDE.md` and every rule again). After a refusal, remove the leftover with `git worktree unlock <path>` then `git worktree remove --force <path>`, and delete its `worktree-agent-*` branch. The main session never Reads or Edits a path under `.tmp/wt/<name>/` (each touch injects that worktree's `CLAUDE.md` and every path rule again); even a one-line fix there goes to the part's own subagent or a `.tmp/` patch script run through `node .tmp/in.js`.

A worktree made by `git worktree add` has no `.tmp/` folder, so a tool writing its output there fails: scripts write outputs to the main tree's `.tmp/<name>/` and the brief says so.

A hunt whose deliverable is one test file writes and runs it in the main tree's `.tmp/<name>/` against the worktree's code, and copies it in by one `.tmp/` script just before the commit; so does a design or spike part with its new files (test, module, design note).
