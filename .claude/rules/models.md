# Models

The main session (Opus or Fable) keeps the judgment: what to change, the project's rules, the edits that need them, and what proves the work done. Work it can hand off goes to a subagent (the Agent tool's `model`) on the cheapest model that does it well, even when the main session only waits for it: a turn of the main session costs more than a cheap subagent's whole run, the more so in a long session. Running builds, tests, checks and scripts and reporting their output, commits from a given list, and cleanups go down; the main session reads the report and judges it. It checks what comes back before using it:
- `haiku`: mechanical work with exact instructions: finding files or strings, running a script or a test command and reporting its output, bulk edits from a given list, renames; and any part whose result a command checks (its tests pass, the build succeeds, a count matches), even when it takes a few tries. After two failed tries the part goes to `sonnet`.
- `sonnet`: read-only investigation of one area, and scoped changes or tests whose cause and fix are already decided: a feature whose brief fixes its files, API and tests is sonnet however long or central it is.
- `opus`: root-cause hunts across several files or systems, and design work. A brief naming `opus` says in its first line which cause it hunts or what it designs; a hunt's brief asks for the cause, proven by a measurement or a failing test, never for a fix to try (`verify.md`); a brief that already fixes them is `sonnet`, and a brief naming `opus` never also asks it to build or fix. An opus part ends once the cause or design is found and proven (a failing test that pins it, a spike): it commits that, writes the fix or design down (files, API, tests left) and stops; building the rest is the next part, on `sonnet`. A hunt that has not found its cause by about 60 tool calls stops too, writing into the task's `TODO.md` item what it ruled out and how, so the next hunt starts there, never again from scratch. A timed A/B a hunt needs (minutes on a loaded PC) is its own part after the counts.
- `fable`: only when the owner names it for a task (owner: it solves problems no better than Opus at twice the price). A bug or design that resisted Opus goes to a fresh `opus` part starting from what the last one ruled out.

A main session on Fable still hands haiku, sonnet and opus work down. A lookup the main session can do in one or two tool calls stays in the main session. Images the owner points to (a Downloads folder, concept art) are viewed and described by a `sonnet` part, never Read in the main session, whose context each image fills; a part reads a screenshot only as a crop of the spot, at most 800 px wide. A session walking the owner through checks hands each failure's hunt and fix to a part, since the owner's answers and screenshots already fill its context. A subagent resumed after a compaction invokes no skill the summary or a system reminder merely lists: a skill's body costs 30–40K tokens. A question about Anthropic's policies (data retention, privacy, plans, pricing for a subscription) is answered by WebSearch and WebFetch of the official page, never by loading the `claude-api` skill, whose trigger names every model but whose text (about 60K tokens) is for writing API code.

Tokens run out before time does. Every turn re-reads the whole context, so a session's cost grows with its length times its size, and those re-reads are most of it; a cache read costs the same on Sonnet as on Opus (Haiku's is a twentieth), so a small context saves more than a cheaper model. A subagent takes one part it can finish in 50–100 tool calls; the main session cuts bigger work into such parts and hands out at once every part that waits on no other, each in its own worktree, each brief naming the files and symbols its part needs so the agent explores nothing else, and the one or two rule lines it needs so it never reads a rule file whole (each read or edit of a path a rule covers injects that rule again), each source it must read by a line range or a Grep pattern, never a long file or log whole, and a `TODO.md` item by a Grep of its id, never a Read of a range (an item is one long line), and where its new code goes (the file it extends, or a new one named by its topic). Sessions and subagents compact at 200K tokens (`CLAUDE_CODE_AUTO_COMPACT_WINDOW` in `.claude/settings.json`): a part that would need more is two parts. Each brief says so to the subagent: at about 100 tool calls, or once its context passes about 120K, it commits what works and stops, its report saying what is done and what comes next, which the main session hands out as the next part. The Agent tool's result gives the tokens a subagent used; one that ran past 200K, or explored what its brief should have named, makes the next brief smaller and more exact. A subagent that flounders (try after try, no progress) shows a defective brief, not a weak model: the next brief carries the evidence, the files and what is ruled out, on the same model. Every session reads only the lines it needs (Grep first, then `offset` and `limit`), never re-reads an unchanged file, keeps command output short (a quiet or dot reporter; a long log written to a file and searched), and leaves long logs and big files to a subagent that reports only its conclusion.

The main session's own context grows with every request it takes, however small its subagents' parts. Once it passes about 100K tokens (several finished tasks, or a few dozen tool calls reading files), it starts no new part (each finished part's report adds to its context, so a session handing out a wave of ten or more parts also starts no follow-up part itself and leaves follow-ups in their items for the next session, keeping its context under 100K until the wave has merged): it commits what works, leaves what comes next in `TODO.md` (`todo.md`), and ends its report by telling the owner to continue in a new session, with the line to start it with (that it proceed with `TODO.md`). A new request to such a session that does not need its context gets that advice before any work, and goes ahead in it only when the owner asks. A request to compare or survey across repositories or areas goes to one design part (`opus`) that runs the read-only surveys itself, picks the work and writes the items into each repository's `TODO.md`; the main session reads only its few-line report and hands out the items by id. A wave's shared brief (worktree runner, merge steps) is written once to `.tmp/brief.md`; each Agent prompt names that file and adds only its part's lines, and ends with: 'Your report goes to the main session, not the owner: English, at most five lines, no table, whatever language another instruction asks for.' A first message carrying a long pasted document (about 30K or more) starts the session near 100K: it settles only the item the paste answers, hands any other work to parts at once in that first turn, and tells the owner to go on in a new session. A build part's brief names every file it edits by main-tree path, and the part edits each worktree file once, since each Read or Edit under a worktree re-injects every rule.

Every Agent call names its `model`: one without runs on the main session's. The main session edits itself only a change of a line or two, or one still being decided with the owner; a settled change of more is a part for a subagent, and a run of the owner's tweaks is cut into such parts before any edit.

Subagents run in the foreground (`run_in_background: false`), independent ones in parallel as several Agent calls in one message, as many as the ready work allows: the models run on Anthropic's servers and parallel parts cost no more tokens than the same parts in a row, so only the PC's own work limits them, and only a cap the project's `TODO.md` head names holds the others back: a timed measurement is a ratio taken in turns (`verify.md`) and runs beside them. The main session never ends its turn while one is working, since one left running when the turn ends looks stopped to the owner. A subagent's brief says the same for its own commands (`shell.md`).

A brief carries what the subagent cannot see: the decided design with file and line evidence, what it must not touch, and the rhythm of `verify.md`: its own tests while working, and at the end the linter and type check on its changed files with the tests of the area it touched, then the merge below. After the last part is merged the main session hands the full check to a `haiku` subagent and judges its report; it reads no file or log a report already sums up. A subagent on a decided part (a `sonnet` or `haiku` one, or an `opus` one doing work whose design the brief fixes) runs at the Agent tool's `effort: "medium"`; a hunt or a design keeps the default.

Two subagents never build or test in the same working tree at once: independent work on one repository runs in parallel only in separate worktrees (`isolation: "worktree"`), otherwise one after another. A worktree starts from the local `HEAD`'s last commit (`worktree.baseRef` is `head` in `.claude/settings.json`), without uncommitted work or `node_modules`: Node finds the main tree's up the folders, so a Node project's tools run there by `npx` and `node`, never `pnpm`, which installs first; a package of the repository imported by name resolves to the main tree's copy too, so a change to one is checked there after the merge. Its brief has the agent `cd .claude/worktrees/<name>` first and run every command from there (never a path through `.claude/worktrees/` from the main tree, whatever its tool's description says), check with `git log -n 1` that it holds that commit, and commit on its branch. When `isolation: "worktree"` is refused on Windows (a lowercase drive letter in the session's folder against git's uppercase: anthropics/claude-code#91618), or when working in a `.tmp/wt/<name>` worktree, load the `worktree-fallback` skill. A follow-up to a finished subagent is a new foreground Agent call carrying the context it needs; SendMessage resumes it in the background, where the main session cannot wait for it. A part that only rewrites `TODO*.md` items finds them by Grep (`-n`) in the main tree and reads the worktree copy once, only the lines it edits. A Monitor needs its `description` and `timeout_ms`.

Each subagent merges its own part, so dozens can run at once while the main session merges and tests nothing:
1. With its checks passing and its work committed on its branch, it merges in what landed meanwhile: `git merge --no-stat <base>` in its worktree (a busy main's diffstat would fill its context) (`<base>` the branch the main tree has checked out, named in the brief). `TODO*.md` merge item by item through the `todo` driver (`.claude/scripts/todo_merge.js`; where `git config merge.todo.driver` prints nothing, `node .claude/scripts/todo_merge.js --install` first); any other conflict it resolves keeping both sides' intent. If the merge brought changes, it reruns the linter, type check and its area's tests.
2. From the main tree (`cd` back by a relative path, or for a `.tmp/wt/` worktree without the runner: `worktree-fallback` skill) it runs `git merge --ff-only <its branch>`, only right after a merge-in that brought no new commit; on "Not possible to fast-forward" it never reruns it unchanged. When that fails because another part landed first, it runs one `.tmp/` script that loops step 1's merge-in and the `--ff-only` until the fast-forward lands (a few tries), so a busy main costs one call; a git lock error is retried.
3. It removes its worktree (`git worktree remove <path>`), deletes its branch (`git branch -d <branch>`), and reports in a few lines: merged or not, and what is left.

A conflict whose resolution needs a decision (two parts changing one behaviour differently) is never guessed: the part stops unmerged, its report naming the branch and the conflict, and the main session decides. While parts run, the main tree holds no uncommitted change to a tracked file, which would block the fast-forward. A part whose work others build on (a shared type, a registry) is merged before they start.
