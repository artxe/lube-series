- The package is ESM only like the others; `engines` follows `@stylistic/eslint-plugin`, and a CommonJS `eslint.config.cjs` reaches it through `require(esm)`. `src/index.js` reads the version from `../package.json`.
- Never slice the whole source per node (quadratic); go through `src/utils/source_text.js`. Its edits are what let the nesting rules (`ascii-order`, `pretty-jsdoc-casting`, `pretty-sequence`) verify at `Program:exit` in reverse order and fix every level in one pass.
- Unit tests miss corruption: check a rule fix for an unchanged AST and unmoved comments on real code (files in node_modules, plus the sveltejs/svelte sources for JSDoc casts and comment-led lines), and check that the recommended and strict configs converge there, on CRLF copies too (no bare LF in the output). `@stylistic/indent` conflicts and fixes dropped for overlapping another rule's fix only show up this way. A `@stylistic` fix that breaks code gets a wrapper in `src/index.js`, not a disabled rule.
- `svelte-naming-convention` is run on the sveltejs/svelte repository (JS with JSDoc checked by tsc, `fixSameNames: true`). Check a change there: clone it, camelCase its snake_case locals and their `@param` names by scope, run the fix and compare the AST and the comments with the original.
- Its fix order is forced: ESLint drops overlapping fixes per pass and espree rejects an exported name that is not declared, so usages go before their declaration (a later pass), a declaration is one fix with its `export { }` specifiers, a name is one fix with its usages whenever a later pass could leave a half-renamed usage resolving to another variable (the snake_case name declared anywhere, same-name variables in nested scopes), writes and `export default` go with the declaration so no other rule sees them split from it (`prefer-const`, `ascii-order`), and a name with a declaration the rule never renames (a merged TS namespace, an `eslint-disable`d line) gets no fix at all.
- Indentation a rule writes must match `@stylistic/indent` or the two cycle: take the base from `source.get_line_indent`, which follows stylistic's offset chain (`@stylistic/eslint-plugin/dist/rules/indent.js`), not the physical line, wherever the two differ, and set it only on line breaks the rule inserts (stylistic measures a ternary that starts mid-line, after `) + (`, from where the enclosing expression starts). Measure every change to `get_line_indent` on the whole corpus before keeping it: a line starting with a closing bracket, `), b, {` or `} of f(`, is indented one level deeper by the indent rule, but following it there (bracket chain, statement chain, physical indent plus one level) breaks corpus files, whose `eslint --fix` then cycles. The indent rule is not self-consistent either: with CR line breaks it indents JSX differently than with LF, and in a `.svelte` file it never fixes the top level of `<script>` while it still offsets the lines below from where that code should be.
- Without semicolons a `(` after a type comment can be the arguments of a call: read the node at that parenthesis before treating it as a casting, and never move white space out of the parentheses a fix removes, or the fix fights `pretty-sequence` forever.
- `maxLength` of `pretty-sequence` and `pretty-imports` counts the columns a line takes, so `src/utils/text_width.js` gives a Korean, Chinese or Japanese character the width 2. Counting UTF-16 units instead let a Korean line stay on one line at twice the width of a Latin one the rule had already broken. The message names the width it measured, never "fit in `maxLength`", because the number covers the items alone, without the code around them.
