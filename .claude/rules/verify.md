# Verification

A change builds what its request names and nothing more (no delete or undo function, migration, fallback or switch it did not ask for): a change that leaves old data behind says what a migration would touch, and builds it only when asked.

Formatting and every fix a linter can make are the linter's: write the code, run the project's fixer on the changed files (`npx eslint --fix <files>`, `cargo clippy --fix`), and edit by hand only what it reports and cannot fix. Never hand-format first.

While working, run only the tests the change touches: one test file, one class, one `--tests` filter, the fuzzer or simulation of the part changed. The project's full check (lint, the whole suite, a clean build) runs once when the task is done, and again only after fixing what it found; in a run of several tasks (a session working through `TODO.md`), once after the last of them: the last the session does (none ready is left, or it stops), not the last in `TODO.md`, which may never empty. A session that merges work it cannot check before it stops writes at the top of `TODO.md` that the full check is owed since that commit; the next session runs it first. A slow measurement (a duel, a benchmark, a long fuzz run) runs only when the change can move it. Speed tests (how the time grows with the work) live apart from the bug tests: in their own files, which the default test run and the full check leave out, run alone on a quiet PC by a change that can move a speed; deterministic work counts (calls, bytes, nodes visited) stay with the bug tests.

A bug or a missed goal is found before it is fixed. A hunt first lists the levels its cause can sit at, lowest first (the test's setup against what the domain allows, the layer under the feature measured alone, that layer's known limits, the numbers and units, the feature's own logic), each with the cheapest measurement that clears or convicts it, and clears them in that order, beside how published work and established implementations solve the same problem (their documentation through WebSearch and WebFetch, read before the first fix, not after the tenth); a fix is tried only at a level whose lower levels are cleared. A failed fix widens the hunt, never deepens it: the next part measures a level the fix assumed sound or takes another approach from those sources, never a variant of the same fix. A hunt writes down a hypothesis, the measurement that would refute it and the number it predicts, then measures; the code changes only once a measurement shows one quantity wrong at its source and by how much, and the fix states the number it will bring. A change tried without that is a guess, and guesses are not tried. A goal judged by an aggregate (a win rate, a score, a frame time, a percentage off) is tuned by the quantities that make it, never by the aggregate alone. After two failed fixes at one goal, however they failed, nobody fixes it again until a new measurement explains both failures. The goal's `TODO.md` item counts the parts spent on it (`parts: 3`); a goal still missed after three parts goes to the owner as a decision (`todo.md`: keep it, loosen the bound to what was reached, or drop it), and its work waits for the answer. Before it goes, check the test's own setup against what the domain allows (in physics, a body the test expects to rest that cannot, as a cube floating at density 0.21–0.79 tips; a target value ignoring the walls): a wrong setup is a bug fixed first and counts as no part. And `CLAUDE.md` may settle the question: an exact mode never loosens below what it is for, and a goal the default cannot meet cheaply splits into a simple default and the exact form as an option; then Claude decides, and only the time it costs is the owner's. The item holds the facts measured so far that narrow the cause, the next measurement, and the failed fixes, at most three lines (what changed, the number it predicted, what came), the oldest dropped first, never a history of what each part did.

A test exists for one of two reasons: written first, it states a new behaviour the change then makes pass; kept, it stops a later change from breaking a behaviour that works (a fixed bug among them). So a test states what the code does for its user, at the outermost level that reaches it, one test per behaviour: never one written to reach a line or a branch, to repeat what another test states, or to pin how the code does it (a private helper, a call order, a message's wording). Coverage is no goal: it has no threshold and runs only when asked. A test found to break that is deleted, or rewritten to state the behaviour when no other test does.

A test catches only a regression, never an improvement, and is written so from the start: a number it checks is bounded on the side a regression moves it (work, time, bytes, a count of compiles or calls at most what it is; accuracy, a share hit at least), never pinned exact where doing better would also change it; an exact value only where it is the behaviour itself (a result, a state hash, pixels matching).

A test reads nothing outside the repository and bounds no wall-clock time (a loaded PC runs several times slower): speed is stated by how the time grows with the work, both sizes timed in turns. The owner may be using the PC meanwhile: every browser a check or test starts is headless and muted, and nothing that opens a window or loads the high-performance GPU runs without the owner's go; a headless browser on the low-power GPU is free to use.
