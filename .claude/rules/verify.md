# Verification

A change builds what its request names and nothing more (no delete or undo function, migration, fallback or switch it did not ask for): a change that leaves old data behind says what a migration would touch, and builds it only when asked.

Formatting and every fix a linter can make are the linter's: write the code, run the project's fixer on the changed files (`npx eslint --fix <files>`, `cargo clippy --fix`), and edit by hand only what it reports and cannot fix. Never hand-format first. After the fixer, Grep a fixed file's text before the next Edit of it: the fixer re-wraps and reorders lines, so an Edit from the text read before fails. Before an Edit of a block spanning several lines, Grep it with `-C` for its exact tabs (the Read tool's line-number prefix hides how many tabs lead a line); a failed Edit is retried only after that Grep, never with a guessed variant. Before a bulk transform of a committed data file, run the tests that read that file against a scratch copy; a transform they then fail is reported as a decision, never applied and undone. The fixer runs only on the files a part changed (never a folder, which rewrites unrelated files) and again after the last Edit of a file; it reorders top-level declarations, so a patch script never cuts a file by the index of a text it appended earlier. A command that fails on its first try is read for its error text before any variant is tried. An Edit of a worktree file needs that exact path Read first in the session (a Read of the main tree's copy does not count); a multi-line Edit that fails once is replaced at once by a `.tmp/` patch script, whose idempotence marker is a token of the new code, grepped in the target before the script is written (a marker the file already holds skips its step silently), and whose `from` for code the fixer may re-wrap is written after the fixer ran, with `\s*` between tokens.

While working, run only the tests the change touches: one test file, one class, one `--tests` filter, the fuzzer or simulation of the part changed. The project's full check (lint, the whole suite, a clean build) runs once when the task is done, and again only after fixing what it found; in a run of several tasks (a session working through `TODO.md`), once after the last of them: the last the session does (none ready is left, or it stops), not the last in `TODO.md`, which may never empty. A session that merges work it cannot check before it stops writes at the top of `TODO.md` that the full check is owed since that commit; the next session runs it first. A slow measurement (a duel, a benchmark, a long fuzz run) runs only when the change can move it. Speed tests (how the time grows with the work) live apart from the bug tests: in their own files, which the default test run and the full check leave out, run by a change that can move a speed; deterministic work counts (calls, bytes, nodes visited) stay with the bug tests.

A bug or a missed goal is found before it is fixed. A change tried without a measurement that shows one quantity wrong at its source is a guess, and guesses are not tried. After two failed fixes at one goal nobody fixes it again until a new measurement explains both failures. A hunt for a cause (several levels, hypotheses, ablations, parts counted in its `TODO.md` item) follows the `hunt` skill: load it before starting one.

A test exists for one of two reasons: written first, it states a new behaviour the change then makes pass; kept, it stops a later change from breaking a behaviour that works (a fixed bug among them). So a test states what the code does for its user, at the outermost level that reaches it, one test per behaviour: never one written to reach a line or a branch, to repeat what another test states, or to pin how the code does it (a private helper, a call order, a message's wording). Coverage is no goal: it has no threshold and runs only when asked. A test found to break that is deleted, or rewritten to state the behaviour when no other test does.

A test catches only a regression, never an improvement, and is written so from the start: a number it checks is bounded on the side a regression moves it (work, time, bytes, a count of compiles or calls at most what it is; accuracy, a share hit at least), never pinned exact where doing better would also change it; an exact value only where it is the behaviour itself (a result, a state hash, pixels matching).

A test reads nothing outside the repository and bounds no wall-clock time (a loaded PC runs several times slower): speed is stated by how the time grows with the work, both sizes timed in turns. A speed change is shown by a ratio measured on one PC in turns against a base (the commit before, or a reference library's same scene): that it helps and nothing regresses, never that a target was reached; never an absolute time, which follows the PC (owner). Both sides of a ratio share the PC's load, so it needs no quiet PC and runs beside other work (owner): interleaved rounds, medians, more rounds or an A/A run when the spread is wide. The owner may be using the PC meanwhile: every browser a check or test starts is headless and muted, and nothing that opens a window or loads the high-performance GPU runs without the owner's go; a headless browser on the low-power GPU is free to use.
