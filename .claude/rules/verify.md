# Verification

Formatting and every fix a linter can make are the linter's: write the code, run the project's fixer on the changed files (`npx eslint --fix <files>`, `cargo clippy --fix`), and edit by hand only what it reports and cannot fix. Never hand-format first.

While working, run only the tests the change touches: one test file, one class, one `--tests` filter, the fuzzer or simulation of the part changed. The project's full check (lint, the whole suite, a clean build) runs once when the task is done, and again only after fixing what it found; in a run of several tasks (a session working through `TODO.md`), once after the last of them: the last the session does (none ready is left, or it stops), not the last in `TODO.md`, which may never empty. A session that merges work it cannot check before it stops writes at the top of `TODO.md` that the full check is owed since that commit; the next session runs it first. A slow measurement (a duel, a benchmark, a long fuzz run) runs only when the change can move it.

A goal judged by an aggregate (a win rate, a score, a frame time) is tuned by the quantities that make it, never by the aggregate alone. When two tries at one goal fail the same way (one case improves as another worsens, or the number does not move), the next part is no third try: it builds the measurement that shows which part is wrong and by how much (each part's prediction against what happened), and later tries work from its numbers. The goal's `TODO.md` item keeps one line per failed try (what it changed, which case got worse) so a later session sees the run, until the measurement's numbers replace them; an item whose cause is unknown names the measurement that would find it.

A test exists for one of two reasons: written first, it states a new behaviour the change then makes pass; kept, it stops a later change from breaking a behaviour that works (a fixed bug among them). So a test states what the code does for its user, at the outermost level that reaches it, one test per behaviour: never one written to reach a line or a branch, to repeat what another test states, or to pin how the code does it (a private helper, a call order, a message's wording). Coverage is no goal: it has no threshold and runs only when asked. A test found to break that is deleted, or rewritten to state the behaviour when no other test does.

A test reads nothing outside the repository and bounds no wall-clock time (a loaded PC runs several times slower): speed is stated by how the time grows with the work, both sizes timed in turns. The owner may be using the PC meanwhile: every browser a check or test starts is headless and muted, and nothing that opens a window or loads the GPU runs without the owner's go.
