# Shell commands

The `allow` rules of `.claude/settings.json` apply only once this folder is trusted on the PC (Claude Code's workspace trust; `ask` and `deny` apply regardless). The VS Code extension never shows the trust dialog, so on a new PC or for a new project folder: run `claude` once in a terminal in the folder and accept, or set `projects["<folder>"].hasTrustDialogAccepted` to `true` in `~/.claude.json` (`<folder>` the repository root as Claude Code writes it: a lowercase drive letter and forward slashes), then start a new session. When `/permissions` lists no allow rules, or a command an allow rule covers still asks, the folder is not trusted: say so to the owner instead of working around it.

Edits under `.claude/` ask every time: Claude Code's safety check for it (like `.git`) runs before every allow rule, so no allow rule turns it off. Its prompt offers only answers for the session (a skill's folder, or accepting edits), never a line in the settings; no `ask` rule names `.claude/`, which would hide that answer for a skill. Make the edits under `.claude/` together, so the owner answers once.

Claude Code asks the owner about any Bash or PowerShell command its checker cannot fully read, allow rules or not, and each "don't ask again" answer adds a one-off line to the project's settings. Keep every command one plain, readable call:
- One command per call: no `;`, `&&` or `||` joining commands, no `(...)` subexpressions. Compare files with `git diff --no-index a b`.
- No pipes into filters and no redirection (`| head`, `| tail`, `| grep`, `| Select-String`, `| Select-Object`, `>`, `>>`, `2>&1`): shorten output by the tool's own options (`npx vitest run <files> --reporter=dot`, `git log -n 5`), and let a script write its output to a file named by an argument, read then with the Read or Grep tool.
- No shell variables, loops, functions or command substitution (`S=...`, `$x = ...`, `for`, `while`, `until`, `foreach`, `$(...)`): anything more than one command is a script in `.tmp/`.
- No inline scripts (`node -e`, `python -c`, `python -` with a heredoc, a PowerShell here-string run as code): write the script to a file in `.tmp/` and run `node .tmp/<file>` or `python .tmp/<file>`.
- Temporary work (one-off scripts, their outputs, temporary tests) goes in `.tmp/` at the project root, which git ignores, never outside the project (the session scratchpad, whatever the session is told about one, or the system temp folder): every file and command there asks the owner.
- Paths in commands are relative to the project. `cd` (and `Set-Location`) only by a relative path, as a command of its own (`cd sub/folder`, `cd ..`); pass a folder to a tool instead where it takes one (`git -C dir`).
- A program run by its path: `dir/prog` with forward slashes (`.venv/Scripts/python.exe -m app`, `./scripts/build.ps1`), or in PowerShell `.\dir\prog`; never `dir\prog.exe` (PowerShell's checker then sees only `prog.exe`, so no allow rule applies) and never through `&`.
- No PowerShell argument holding a variable or an expression (`-Confirm:$false`, `"$x"`, `(Get-Location)`, `@(...)`): no allow rule covers it, whatever the tool's own description suggests; `Remove-Item -Recurse -Force` does not prompt without `-Confirm:$false`. Give a path cmdlet one path, not a comma list.
- ASCII only: no Hangul or symbols such as `×` in a command. Search text with the Grep tool.
- No environment variables set for a command (`NAME=value cmd`, `set`, `export`, `$env:NAME = ...`): the command then starts with the variable, not with the allowed program. Pass values as arguments or in a file; a tool that reads them only from the environment runs as `node --env-file=.tmp/<name>.env <its script>` (for vitest, `node --env-file=.tmp/<name>.env node_modules/vitest/vitest.mjs run <files>`).
- Web pages and web APIs through WebFetch, not `curl`; `curl` only to a server on this PC (`localhost`, `127.0.0.1`). GitHub through the read commands of `gh` (`gh search`, `gh issue view`, `gh pr view`, `gh release view`, `gh repo view`).
- Builds and tests run in the foreground with the tool's timeout (up to 10 minutes a call). Only a server, or a command that cannot finish in 10 minutes, runs in the background (the tool's `run_in_background`); the session waits for it before ending its turn and stops it with TaskStop, never by its process id (`Stop-Process`, `taskkill`).
- Change files with the Edit and Write tools, not `sed -i` or `perl -pi`; a change over many files is a script in `.tmp/`.
